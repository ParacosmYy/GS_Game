# 角色协同模板

每轮迭代先执行 3 个自侦测角色，再决定是否升级到 6-9 人深审编队。

- 自侦测是每轮必做的前置门。
- 深审编队只用于高风险任务、黄/红自侦测结果，或用户明确要求。
- 当前若任务与 Ryo 内容包相关，所有角色都必须区分“兼容入口”与“真实数据迁移层”，不要把 README 或目录骨架误判成已完成数据。
- 当前若任务与 Phase 2 多角色内容包相关，所有角色都必须区分 Ryo / Kyo / Iori 以及共享 contract，不要把单一角色的结论误判为全局结论。
- 所有角色在给结论前，先对照 [KOF 差距矩阵](../product/kof-gap-matrix.md)，明确自己是在闭合哪一项差距。

如果工具环境无法创建子 agent，主 agent 必须明确说明原因，并在同一轮中按本文模板逐项模拟这些角色的结论。不得写成“已调用子 agent”。

## 0. 3 人自侦测编队

### 0.1 架构自检

关注：

- 是否触发迁移、换栈、目录扩张或大搬家。
- 是否违反模块依赖方向。
- 是否留下回退路径。
- 是否超出当前主线。

### 0.2 研发自检

关注：

- 是否可实现。
- 是否能小步落地。
- 会影响哪些文件。
- 是否需要新增测试或脚本。

### 0.3 产品自检

关注：

- 是否仍服务 `Ryo Vertical Slice`。
- 是否对玩家真的有价值。
- 验收标准是否清楚。
- 是否在扩 scope。
- 是否明确对应差距矩阵里的某一项差距。

## 1. 深审编队（6-9 人）

当自侦测通过且任务需要更深的审查时，再启动深审编队。默认必须并行调用 8 个子 agent；允许范围为 6-9 个。

默认角色配比：

- 2 个架构师。
- 4 个研发工程师。
- 1 个产品经理。
- 1 个测试负责人。

如果任务特别小，深审时最低也必须 6 个角色；如果任务涉及换栈、资产管线或大迁移，建议 9 个角色。

## 2. 深审编队：默认 8 角色

### 2.1 架构师 A：总架构与边界

关注：

- 是否符合 [工作区目标架构](../architecture/workspace-architecture-target.md)。
- 是否保持 `app / engine / simulation / content / rendering / audio / tools` 分层。
- 是否需要新增目录、迁移目录或保留兼容层。
- 是否违反模块依赖方向。
- 是否让文件池更清晰，还是只是在制造更多文件。

### 2.2 架构师 B：Frame Contract 与资产管线

关注：

- 视觉帧、判定帧、反馈事件是否同源。
- manifest 是否可验证。
- 运行时是否只消费 manifest。
- 工具层是否和运行时分离。

### 2.3 研发 A：simulation / combat

关注：

- Fighter 状态、物理、hit resolution。
- hitstop / hitstun / pushback / cancel。
- replay determinism。

### 2.4 研发 B：content / character

关注：

- Ryo content package。
- stats、commands、frameData、animations、hitboxes、feedback。
- 哪些仍是兼容入口，哪些已经进入真实数据层。
- 角色数据是否泄露到通用系统。
- 该角色是否被拆成了清晰的文件池，还是仍然堆在一个大文件里。

### 2.5 研发 C：rendering / animation

关注：

- Canvas2D 渲染。
- sprite / skeletal fallback。
- debug overlay。
- 视觉帧是否来自 manifest。

### 2.6 研发 D：tools / asset pipeline

关注：

- atlas 生成。
- manifest validator。
- completeness report。
- 资产授权与来源记录。

### 2.7 产品经理

关注：

- 玩家价值。
- 本轮是否让 Ryo 更像 KOF。
- 验收标准。
- 非目标和 scope 控制。

### 2.8 测试负责人

关注：

- 自动测试。
- 手测路径。
- 回归风险。
- 质量门禁。
- 文件池拆分是否有对应验证。

## 2.9 可选第 9 角色

当任务涉及参考资料、SNK/MUGEN/IKEMEN 对标或大型迁移时，可增加：

- 参考研究员：只研究公开资料和本地 `references/`，不得复制商业素材。
- 发布/集成负责人：关注构建、chunk、CI、分支、提交边界。

## 3. 自侦测模板

### 3.1 架构自检

```text
角色：架构自检

请输出：
1. 本轮是否触发迁移、换栈、目录扩张或大搬家。
2. 是否违反模块依赖方向。
3. 是否留下回退路径。
4. 是否仍服务当前主线。
5. 是否让文件池更清晰，还是只是在制造更多文件。
6. 结论：green / yellow / red。
7. 理由与风险。
```

### 3.2 研发自检

```text
角色：研发自检

请输出：
1. 是否可实现。
2. 会影响哪些文件。
3. 是否能小步落地。
4. 是否能按文件池拆成 state / transitions / effects / selectors。
5. 是否需要新增测试或脚本。
6. 结论：green / yellow / red。
7. 理由与风险。
```

### 3.3 产品自检

```text
角色：产品自检

请输出：
1. 是否仍服务 Ryo Vertical Slice。
2. 是否对玩家真的有价值。
3. 验收标准是否清楚。
4. 是否在扩 scope。
5. 是否明确改善了单文件职责，而不是继续堆大文件。
6. 结论：green / yellow / red。
7. 是否明确对应差距矩阵里的某一项差距。
8. 理由与风险。
```

## 4. PM 模板

```text
角色：产品经理
主线：Ryo Vertical Slice

请输出：
1. 本轮解决的玩家问题。
2. 它属于 Ryo 的哪条闭环：肖像 / sprite / animation / hitbox / feedback / 工具 / 文档。
3. 为什么现在做它。
4. 本轮范围。
5. 本轮非目标。
6. 验收标准。
7. 完成后更像 KOF 的具体表现。
8. 是否允许本轮 +1，理由是什么。
```

## 5. 玩家模板

```text
角色：玩家/文件用户

请输出：
1. 当前第一眼最不像 KOF 的点。
2. 当前操作时最破坏打击感的点。
3. Ryo 本轮必须改善的一个体验。
4. 本轮不能退化的体验。
5. 玩家如何判断它真的变好了。
```

## 6. 研发模板

```text
角色：研发工程师

请输出：
1. 本轮改动文件。
2. 每个文件职责变化。
3. 新增或修改的数据结构。
4. 是否涉及 Frame Contract。
5. 需要新增或更新的测试。
6. 不应触碰的文件。
7. 回退方案。
```

## 7. 测试/文档模板

```text
角色：测试与约束文档负责人

请输出：
1. 自动测试命令。
2. 手测路径。
3. 需要同步的文档。
4. 需要防止的旧方向：堆角色 / 修 placeholder / 盲目换栈 / 堆模式。
5. 本轮闭合了差距矩阵中的哪一项。
6. 本轮完成后如何记录评分。
7. 是否涉及多角色内容包或流程仪式感。
```

## 8. 架构师模板

```text
角色：架构师

请输出：
1. 是否保持运行时只消费 manifest。
2. 是否保持工具层和运行时分离。
3. 是否保持 rendering 不决定 combat。
4. 是否保持 combat 不依赖 rendering/audio/DOM。
5. 是否让 Frame Contract 更完整。
6. 是否触发技术栈决策门。
7. 是否会妨碍未来 PixiJS/WebGL/Godot 迁移。
```
