# 角色协同模板

本文件用于每轮迭代前的多视角评审。可以由多个子 agent 分别执行，也可以由主 agent 在同一轮中模拟输出。目标是避免只从代码角度推进，导致产品体验继续偏离 KOF/QF。

## 1. 产品经理模板

```text
角色：产品经理
任务：把本轮迭代压缩成一个可验收、可交付的小目标。

请输出：
1. 本轮要解决的玩家问题。
2. 为什么现在做它，而不是做别的。
3. 本轮范围。
4. 本轮非目标。
5. 验收标准。
6. 对 KOF/QF 接近度的贡献。
7. 失败风险和回退方式。
```

## 2. 玩家/文件用户模板

```text
角色：玩家/文件用户
任务：站在真实使用者角度指出体验落差。

请输出：
1. 第一眼最不像正版的点。
2. 实际操作时最破坏沉浸的点。
3. 本轮最不能退化的体验。
4. 如果只能改一个问题，应该改什么。
5. 完成后玩家如何判断它变好了。
```

## 3. 研发模板

```text
角色：研发工程师
任务：把需求拆成最小实现步骤。

请输出：
1. 改动文件列表。
2. 每个文件的职责变化。
3. 数据结构变化。
4. 需要新增或更新的测试。
5. 不应触碰的文件。
6. 潜在冲突和回退方案。
```

## 4. 测试/文档模板

```text
角色：测试与约束文档负责人
任务：保证本轮可验证、可复盘、不会污染长期规则。

请输出：
1. 自动测试清单。
2. 手测清单。
3. 需要更新的文档。
4. 需要删除或归档的过期文档。
5. 本轮完成后评分是否可 +5，以及理由。
```

## 5. 架构师模板

```text
角色：架构师
任务：检查本轮是否让项目更可维护、更接近未来引擎形态。

请输出：
1. 模块边界是否清晰。
2. 是否引入反向依赖。
3. 是否有角色硬编码进入通用系统。
4. 新状态的归属、生命周期、reset、snapshot/replay 影响。
5. 是否影响未来 PixiJS/WebGL/Godot 迁移。
6. 是否需要触发技术栈决策门。
```

## 6. 汇总格式

每轮实施前，最终汇总成：

```text
本轮目标：
- ...

PM 结论：
- ...

玩家结论：
- ...

研发方案：
- ...

测试/文档方案：
- ...

架构结论：
- ...

验收标准：
- ...

不做事项：
- ...
```
