# 决策门

本文规定每类重大决策如何判断、何时允许做、做完如何验收。后续 AI 必须按本文执行，不得凭感觉推进。

## 1. 总决策原则

每个决策必须回答：

- 它服务 Ryo Vertical Slice 吗？
- 它让 Frame Contract 更完整吗？
- 它降低了资产、动作、判定、反馈或稳定性风险吗？
- 它是否会扩大 scope？
- 它如何验证？
- 它如何回退？

如果回答不清楚，不实施。

## 1.1 自侦测前置门

每轮在进入实施前，必须先完成 [自侦测前置](self-detection.md)。

允许条件：

- 架构自检为 `green`，或虽为 `yellow` 但已明确补方案路径。
- 研发自检为 `green`，或虽为 `yellow` 但已明确文件边界与测试影响。
- 产品自检为 `green`，或虽为 `yellow` 但已明确验收与范围。

拒绝条件：

- 任一角色为 `red`。
- 3 个角色的结论彼此矛盾且无法收敛。
- 还没完成自侦测就直接进入代码改动。

## 2. 新功能决策门

允许条件：

- 直接服务当前 Phase 2 主线。
- 能明确对应 [KOF 差距矩阵](../product/kof-gap-matrix.md) 的某一项差距。
- 有验收标准。
- 有测试或手测路径。
- 不新增无关角色/模式。

拒绝条件：

- 只是“看起来更丰富”。
- 只是新增系统名词。
- 不能解释更像 KOF 在哪里。

## 3. 架构迁移决策门

允许条件：

- 迁移目标写在 [工作区目标架构](../architecture/workspace-architecture-target.md)。
- 只迁一个领域。
- 不改变行为，或行为变化有测试。
- 保留兼容层。

本轮必须输出：

- 旧路径。
- 新路径。
- 迁移原因。
- 依赖方向。
- 验证命令。
- 回退方案。

## 4. 资产管线决策门

允许条件：

- 定义了 manifest schema。
- 有 validator 或测试。
- Ryo 至少接入一个资源或动作。
- fallback 仍可用。

拒绝条件：

- 未确认许可。
- 直接把研究资源放进运行时。
- 只加图片，没有 manifest。

## 5. 角色扩展决策门

在 Phase 2 的角色内容包和共享 contract 不稳定前，默认拒绝新增“无契约”的角色。

Phase 1 基线条件见 [Ryo Vertical Slice](../product/ryo-vertical-slice-plan.md)。

允许 Kyo/Iori 的条件：

- Ryo 8 个基础动作完成。
- Ryo select/HUD 肖像完成。
- Ryo light/heavy feedback 完成。
- Ryo 完整度报告可运行。
- Kyo/Iori 角色内容包和 content loader 已接入统一入口。
- Kyo/Iori 的新增内容不破坏现有 shared contract / Frame Contract。
- 构建和测试通过。

## 6. 打击感决策门

允许条件：

- 改动绑定 hit event。
- 明确属于 light/heavy/special/DM 哪档。
- 视觉、音频、震屏、hitstop 不互相抢权。
- 有手测路径。

拒绝条件：

- 只加特效。
- 只改颜色。
- 不区分命中和防御。
- 不区分轻重攻击。

## 7. 技术栈决策门

默认不换栈。

允许评估条件：

- Ryo 已接入真实或准正式 atlas/manifest。
- Canvas 2D 出现可复现性能或能力瓶颈。
- simulation 与 rendering 已解耦。
- 有迁移收益、成本和回退方案。

禁止：

- 因为角色丑而换栈。
- 因为文件乱而换栈。
- 因为“正版应该不是这样写”而换栈。

## 8. 文档修改决策门

允许条件：

- 消除冲突。
- 增强执行闭环。
- 明确新的验收标准。
- 同步相关索引。

拒绝条件：

- 只写口号。
- 产生新的优先级冲突。
- 不更新引用它的文档。

## 9. 目录收口决策门

允许条件：

- 本轮修改能让 Ryo 内容更集中。
- 本轮修改能减少散落的角色专属文件来源。
- 本轮修改能把“一个人物先做精”的执行顺序写清楚。
- 有明确的旧路径、目标路径和回退路径。

拒绝条件：

- 只是为了“看起来更整齐”而搬目录。
- 一次性大范围重排所有角色文件。
- 把收口动作变成新的散点迁移。
- 不能说明为什么这一步服务 Ryo 闭环。

## 10. 文件池决策门

允许条件：

- 目标文件同时承担多个职责，且已经影响可读性或可测试性。
- 可以明确拆成 state / transitions / effects / selectors / tests 或同等职责池。
- 有明确的旧路径、新路径和回退路径。

拒绝条件：

- 只是为了“文件多起来”而拆分。
- 拆分后没有统一出口。
- 拆分后依然让通用模块知道太多角色细节。

本轮必须输出：

- 旧文件职责。
- 新文件职责。
- 统一入口是谁。
- 哪些文件只是过渡层。
- 如何验证拆分没有改坏行为。

```text
为什么允许：
- ...

为什么现在做：
- ...

如何验证：
- ...

如何回退：
- ...
```
