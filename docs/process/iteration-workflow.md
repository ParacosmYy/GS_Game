# 迭代流程

每轮必须形成闭环。若用户明确要求只整理文档或只分析，则按用户指令缩小范围。

## 标准流程

1. **研究**
   - 先查 `references/`。
   - 必要时搜索公开资料。
   - 记录可借鉴点和不能照搬的内容。

2. **需求**
   - PM 视角：本轮价值、范围、验收标准。
   - 玩家/用户视角：体验目标、失败体验、不可退化项。
   - 架构视角：边界、依赖、迁移风险。
   - 角色模板见 [角色协同模板](role-prompts.md)。

3. **方案**
   - 说明改哪些文件。
   - 说明不改哪些文件。
   - 说明完成标准。

4. **实施**
   - 小步改动。
   - 不加无关功能。
   - 不把历史归档当当前规则。

5. **验证**
   - 运行相关测试。
   - 运行 `npx tsc --noEmit`。
   - 运行 `npx vite build`。
   - 涉及玩法时说明手测结果。

6. **评估**
   - 回答“更像正版在哪里”。
   - 回答“仍不像正版在哪里”。
   - 回答“下一轮最该修什么”。
   - 更新评分，每轮只 `+5`。

7. **提交**
   - 中文 Conventional Commit。
   - 正文分点写原因、差异、验证、风险。

## 自动迭代边界

“持续迭代”不等于无目标乱改。没有明确收益、没有验收标准、没有验证路径的改动不得执行。

## 每轮必须回顾

- 产品：是否解决真实玩家能感知的问题。
- 正版接近度：输入、帧节奏、打击反馈、角色气质、流程仪式感哪一项变好了。
- 工程：是否保持模块边界、状态归属、reset、snapshot/replay 可解释。
- 测试：是否有自动验证或明确手测路径。
- 文档：是否出现过期规则，是否需要同步 `AGENTS.md`、`CLAUDE.md` 或 `docs/`。
