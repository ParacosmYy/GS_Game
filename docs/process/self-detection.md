# 自侦测前置

本文定义每轮迭代开始时必须执行的 3 人自侦测。它的作用是先快筛方向，再决定是否需要升级到 6-9 人深审编队。

## 1. 默认编队

每轮开始必须并行执行 3 个自侦测角色：

- 架构自检
- 研发自检
- 产品自检

这 3 个角色是每轮的默认前置门，不是可选项。

## 2. 三个角色分别看什么

### 2.1 架构自检

只看这些问题：

- 是否碰到模块边界。
- 是否触发迁移、换栈、目录扩张或大搬家。
- 是否破坏依赖方向。
- 是否留下回退路径。
- 是否已经超出当前主线。
- 是否让当前样板角色内容更集中，而不是再次散落。
- 是否让文件池更清晰，还是只是把文件数量变多。
- 是否存在可以优先做真实资产导入的路径，而不是继续修骨架或 placeholder。
- 是否存在可以优先闭合 Kyo 样板的路径，而不是先把 Ryo 当作当前第一执行目标。
- 是否存在已导入但尚未接入运行时的 MUGEN 资产（cvskyo/cvsryo/cvskfm PNG sprite），如果有，优先接入它们。
- 是否在试图用截图、静态对照图或屏幕抓图当成主要迭代输入；如果是，直接判定为 yellow/red 并改回真实资产与 manifest。

输出必须给出一个判断：

- `green`：可以继续。
- `yellow`：可以继续研究，但需要更明确的方案或深审。
- `red`：停止实施，先回到决策门。

### 2.2 研发自检

只看这些问题：

- 是否可实现。
- 会影响哪些文件。
- 是否能小步落地。
- 是否需要新增测试或脚本。
- 是否会碰到并行工作区的未完成改动。
- 是否能按文件池把状态机拆成 state / transitions / effects / selectors。

输出必须明确：

- 改哪些文件。
- 不改哪些文件。
- 是否要先补测试。
- 是否要先拆任务。

### 2.3 产品自检

只看这些问题：

- 是否仍服务当前样板角色闭环或公共骨架。
- 是否优先服务 Kyo 的第一样板闭环，而不是继续把 Ryo 当成当前第一执行目标。
- 是否对玩家真的更有价值。
- 验收标准是否清楚。
- 本轮是否在扩 scope。
- 是否让项目更像 KOF。
- 是否在帮助“先把一个人物做精，再复制其他人物”。
- 是否明确改善了单文件职责，而不是继续堆大文件。

输出必须明确：

- 本轮解决什么玩家问题。
- 本轮非目标是什么。
- 完成后如何判断真的变好。

## 3. 结果分流

### 3.1 全绿

如果 3 个角色都是 `green`，并且任务不属于高风险范围，可以进入方案和实施。

### 3.2 有黄

如果任一角色为 `yellow`，必须先补方案细节，必要时升级到深审编队。不能直接开改。

### 3.3 有红

如果任一角色为 `red`，必须停止实施，先改决策或改范围。不得硬上。

## 4. 与深审编队的关系

3 人自侦测是每轮必做的前置门。

6-9 人深审编队是升级门，只用于以下情况：

- 架构迁移。
- 资产管线。
- 角色扩展。
- 打击感系统。
- 换技术栈。
- 大型文档重构。
- 自侦测出现 `yellow` 或 `red` 且需要进一步定案。

## 5. 输出格式

每轮自侦测至少输出：

```text
架构自检：
- 结论：green / yellow / red
- 理由：
- 风险：

研发自检：
- 结论：green / yellow / red
- 理由：
- 风险：

产品自检：
- 结论：green / yellow / red
- 理由：
- 风险：

综合结论：
- 直接实施 / 补方案 / 升级深审 / 停止实施
```

## 6. 约束

- 不能把自侦测写成形式审查。
- 不能省略任一角色。
- 不能把深审编队当作每轮默认负担。
- 不能在自侦测结果为 `red` 时直接进入代码改动。
