# 未来引擎架构与技术栈决策

本文是迁移提案，不是当前强制结构。任何大迁移都必须先得到用户确认。

## 当前默认路线

继续使用 TypeScript + Vite + Canvas 2D，直到出现明确瓶颈。当前最缺的是数据管线、逐帧资产、回放确定性和模块边界，不是框架名。

## 必须评估换栈的触发条件

出现以下任一情况时，必须写技术栈评估：

- Canvas 2D 无法稳定 60fps，且瓶颈来自大量 sprite atlas、粒子、后处理或调色板替换。
- 需要 shader 级效果：palette swap、CRT、bloom、残影、扭曲、批量混合。
- 角色和场景资产进入真实逐帧图集后，加载、缓存、裁剪和内存释放失控。
- 回放/训练/调试需要更严格的确定性和状态快照，当前架构无法继续收敛。
- 资产工具链明显比运行时更复杂，需要独立 pipeline。

## 候选路线

| 路线 | 适用时机 | 代价 |
| --- | --- | --- |
| Canvas 2D 继续强化 | 当前阶段 | 低 |
| WebGL2 自研 2D 后端 | 需要 shader、批处理、atlas | 中 |
| PixiJS | 需要快速获得 WebGL sprite/filter 能力 | 中，增加框架依赖 |
| Rust/WASM 核心 | 需要高确定性模拟或性能热区 | 高 |
| C++/SDL/OpenGL | 另起桌面引擎项目 | 很高 |
| Godot 4 2D | 更重视编辑器和内容制作流程 | 高，迁移成本大 |

## 渐进迁移原则

1. 先把数据和资产边界抽干净。
2. 先让一个样板角色走完整 sprite atlas / frame data / hitbox pipeline。
3. 只有渲染成为真实瓶颈时，才替换渲染后端。
4. 模拟层、角色数据、输入链路应尽量保持可迁移。
5. 不以“更专业”为理由换栈，只以可验证瓶颈和收益换栈。

## 参考源码启发

- IKEMEN GO 把角色、舞台、输入、渲染、回放/rollback、系统加载分开。
- SFF 工具把素材解析、调色板、sprite 导出放在工具链，不混入运行时。
- 我们应学习边界和数据驱动方式，不照搬其完整脚本编译器或历史兼容层。
