# 文件池与状态机拆分约束

本文定义项目中“文件池”的使用方式，以及状态机类文件如何拆分，避免把多个职责堆进一个大文件里。

## 1. 文件池是什么

文件池不是“很多文件随便堆在一起”，而是按职责分组、可替换、可组合的最小文件集合。

一个健康的文件池应满足：

- 每个文件只做一类事情。
- 每个文件都能被单独替换，不影响其他职责。
- 通过 `index.ts` 或 barrel 文件对外暴露统一入口，而不是让上层直接依赖到处散落的实现文件。
- 同一类数据和逻辑可以被拼接，但不能互相污染职责。

## 2. 允许的文件分层

推荐的文件池分层如下：

- `types.ts`：只放类型、接口、枚举。
- `data.ts`：只放静态数据。
- `state.ts`：只放状态机数据与状态枚举。
- `transitions.ts`：只放状态转移条件与转移表。
- `effects.ts`：只放副作用触发入口，不写具体业务判定。
- `selectors.ts`：只放只读查询。
- `render.ts`：只放表现层绘制调用。
- `tests/*.test.ts`：只放验证。
- `index.ts`：只做统一导出，不写核心逻辑。

如果一个文件同时承担“数据 + 状态机 + 过渡 + 副作用 + 渲染”，就说明已经越界。

## 3. 状态机文件拆分规则

状态机类文件必须优先按职责拆，不允许把所有状态都塞进一个“梦文件”。

推荐拆法：

- `xxxState.ts`：承载状态结构、默认值、对外 API。
- `xxxTransitions.ts`：承载状态流转规则。
- `xxxGuards.ts`：承载条件判断。
- `xxxEffects.ts`：承载进入/退出/触发副作用。
- `xxxSelectors.ts`：承载只读查询。
- `xxx.test.ts`：承载状态机测试。

拆分原则：

- 纯状态机逻辑必须尽量无副作用。
- 渲染、音频、DOM 不得进入状态机核心。
- 输入只通过参数进入，不得从全局硬读。
- 每个状态机都应能清楚说明“当前态、下一态、触发条件、退出条件”。

## 4. 文件池的边界约束

### 4.1 允许

- 一个角色包内部按 `commands / moves / attacks / animations / hitboxes / feedback / portraits / reports` 再拆子文件。
- 一个状态机目录里有多个小文件，只要每个文件职责单一。
- 通过 `index.ts`、`barrel.ts`、`manifest.ts` 统一导出。

### 4.2 禁止

- 把多个状态机、多个角色、多个流程塞进同一个大文件。
- 把状态机、渲染、输入、音频混写在一起。
- 用“先放一起以后再说”作为长期策略。
- 让文件池变成“垃圾回收站”。
- 让一个 `switch`、一个 `update()`、一个 `main.ts` 承担所有分支。

## 5. 什么时候必须拆文件

只要满足以下任一条件，就必须考虑拆分：

- 一个文件同时出现 3 种以上职责。
- 一个文件既包含状态定义又包含大量副作用。
- 一个文件既被运行时消费又被测试直接依赖，还承担导出聚合。
- 一个文件的修改历史已经显示它在重复接收无关需求。
- 一个文件需要不同依赖方向，无法继续保持单向依赖。

## 6. 与当前工程的关系

当前工程已经在从单体大文件向文件池化方向迁移：

- `src/state/`、`src/combat/`、`src/content/`、`src/rendering/` 正在承担更清晰的职责。
- 多角色内容包已经出现统一入口，但还需要继续向小文件、强契约、强校验推进。
- 现阶段不要求一次性把所有大文件清空，但要求每次新增都朝“更小、更单一、更可替换”靠拢。

## 7. 文件池验收标准

一个文件池是否健康，至少看这四点：

- 是否能一眼看出每个文件的职责。
- 是否能独立测试核心状态机。
- 是否能通过 barrel 统一接入。
- 是否能在不改通用逻辑的前提下替换单个角色或单个状态。
